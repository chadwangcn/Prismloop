## 一、设计目标

### 1.1 系统定位

整个测试系统**不是人操作,而是由 Agent 驱动**,承载以下三大核心职责 + 后续承接 + 长远规划:

### 1.2 三大核心职责

| 职责 | 目标 | 关键能力 | 优先级 |
|---|---|---|---|
| **职责一:日常单元功能验证** | 开发了日志/语音消息/拍照等功能后,用云手机模拟实际操作去测 | 模拟拍照、说话、发消息、页面点击 | P0 |
| **职责二:多端协同测试** | 设备端和 APP 端按序列操作,验证联动(设备动作→APP 查询/设置/配置→设备联动) | 双端按序操作、状态联动验证 | P0 |
| **职责三:APP 开发验证闭环** | 提供 Figma 设计稿,Agent 开发页面,截图/录像对比设计偏差,驱动迭代 | 截图/录像、视觉 diff、迭代闭环 | P0 |

### 1.3 后续承接

| 职责 | 阶段 |
|---|---|
| 压力测试 | 后续承接 |
| 异常测试 | 后续承接 |

### 1.4 长远规划

整套测试系统**集成到管理后台**:
- 管理后台可**执行测试用例**、下发指令
- 管理后台可**查看测试界面**和结果
- 全程 Agent 驱动,无需人工操作

### 1.5 核心设计原则

1. **全程 Agent 驱动**:测试系统由 Agent 驱动,非人工操作
2. **测试不影响正常业务**:不注册后端回调,不污染生产 webhook 列表,纯用户视角 UI 验证
3. **双端协同**:Guardian APP 与 K1 设备端配对测试,验证业务链路两端状态一致
4. **三层模拟方式**:MUA(自然语言) + SDK(事件级) + ADB(调试),按场景灵活选择
5. **证据可追溯**:每步操作截图/录像,断言失败可回放
6. **云手机为主,真机为辅**:云手机覆盖 80% 协同逻辑测试,真机 K1 补充性能与兼容性测试

### 1.6 基础能力支撑

无论哪个职责,都需要以下基础能力:

| 基础能力 | 说明 |
|---|---|
| 模拟按键 | 物理按键(AI/拍照/电源/音量)、虚拟按键 |
| 模拟操作 | 点击、滑动、多点触控、文本输入 |
| 模拟拍照 | 虚拟摄像头注入视频流 |
| 模拟音频输入 | 虚拟麦克风注入音频 |
| APK 构建与分发 | 云服务器构建→安装→更新 |
| Agent 驱动 | 全程 Agent 驱动,非人工操作 |

### 3.2 节点职责矩阵

| 节点 | 职责 | 与其他节点关系 |
|---|---|---|
| **本地编排器** | 用例管理、Prompt 引擎、断言、报告生成、Pod 配对调度 | 控制所有节点 |
| **构建云主机** | 双 APK 构建、签名、TOS 上传、webhook 通知编排器 | 单向通知编排器 |
| **MUA OpenAPI** | 自然语言驱动任务执行、结构化输出 | 由编排器调用 |
| **客户端 SDK** | 精确事件级操作(按键/点击/多点触控/音视频注入) | 由编排器调用 |
| **ADB 公网直连** | 调试用,本地直接操作云手机 | 由编排器调用(调试模式) |
| **Guardian Pod** | 运行 Guardian.apk,模拟家长端 | 受编排器控制 |
| **K1 Pod** | 运行 K1-Device.apk,模拟儿童端 | 受编排器控制 |
| **Device Platform** | 业务后端(不在测试范围内) | 双端通过业务链路通信 |
| **TOS** | APK 产物、截图、录像、证据存储 | 所有节点可读写 |

### 3.3 数据流

```
1. 构建流:
   构建云主机 ──APK+SHA256──► TOS ──webhook──► 编排器

2. 部署流:
   编排器 ──通知──► Guardian Pod(K1 Pod)──从 TOS 拉取──► 安装 APK

3. 测试流:
   编排器 ──MUA/SDK──► Guardian Pod + K1 Pod ──业务链路──► Device Platform
        └──截图/录像──► TOS

4. 验证流:
   编排器 ──轮询 UI──► Pod 截图 ──MUA 视觉检测──► 断言

5. 证据流:
   TOS ──下载──► 编排器 ──聚合──► 报告
```

## 四、三大核心职责架构

### 4.1 职责一:日常单元功能验证

**场景**:开发完成某功能(如语音消息、拍照、日志)后,用云手机模拟实际操作去测。

```
开发完成某功能(如语音消息)
  ↓
Agent 选择/编写测试用例
  ↓
云手机安装/更新最新 APK
  ↓
Agent 驱动模拟操作(点击/说话/拍照)
  ↓
断言 + 截图/录像
  ↓
报告(通过/失败)
```

**测试覆盖**:
- 功能点正常/空/错误/异步状态
- 模拟拍照、说话、发消息、页面点击
- 物理按键(AI/拍照/电源/音量)
- 音视频注入(扫码、语音输入)

### 4.2 职责二:多端协同测试

**场景**:设备端和 APP 端按序列操作,验证联动。

```
设备端(K1)按序列操作(如拍照)
  ↓
APP 端(Guardian)做查询/设置/配置
  ↓
设备端验证联动(如收到配置变更)
  ↓
双端状态一致性断言
  ↓
报告
```

**协同场景**:绑定、内容下发、报告回传、远程指令、拍照回传、物理按键事件双端感知。

### 4.3 职责三:APP 开发验证闭环

**场景**:提供 Figma 设计稿,Agent 开发页面,截图/录像对比设计偏差,驱动迭代。

```
Figma 设计稿
  ↓
Agent 基于设计稿开发单个页面(遵循 AGENTS.md)
  ↓
APK 构建(云服务器)
  ↓
云手机安装
  ↓
截图/录像(按设计稿的 screen/state 采集)
  ↓
视觉 diff(对比实际与设计)
  ↓
偏差分析(交互/布局/动效)
  ↓
迭代反馈(修复 Critical 偏差)
  ↓
(回到开发,重新闭环)
```

### 4.4 后续承接:压力测试

| 压测场景 | 并发模型 | 双端配对 |
|---|---|---|
| 绑定洪峰 | 50 对 Guardian+K1 同时绑定 | 50 对 Pod |
| 内容下发洪峰 | 50 个 Guardian 同时下发内容 | 50 对 Pod |
| 拍照上传洪峰 | 50 个 K1 同时拍照上传 | 50 对 Pod |
| 混合业务 | 100 对 Pod 随机执行协同用例 | 100 对 Pod |

## 五、三层模拟方式架构

### 5.1 三层方式对比

| 层 | 接入方式 | 精度 | 适用场景 | 生产可用 |
|---|---|---|---|---|
| **MUA 自然语言** | OpenAPI | 视觉语义级 | 复杂流程、UI 变更适应 | ✅ 推荐 |
| **客户端 SDK** | SDK 接口 | 像素级 + 事件级 | 精确坐标、多点触控、键盘事件、音视频注入 | ✅ 推荐 |
| **ADB input** | ADB 公网直连 | 坐标级 | 调试、简单操作 | ⚠️ 仅调试 |

### 5.2 场景适配策略

| 测试场景 | 推荐方式 | 理由 |
|---|---|---|
| 业务流程测试 | MUA 自然语言 | 适应 UI 变更,维护成本低 |
| 精确坐标点击 | SDK sendMouseKey | 像素级精度 |
| 多点触控(缩放/旋转) | SDK sendMulitTouch | 原生支持多点 |
| 物理按键(音量/电源/AI/拍照) | SDK sendKeyCode | 完整按键事件 |
| 中文输入 | SDK sendImeComposition | 支持输入法组合 |
| 音视频注入触发 | ADB broadcast + SDK | 推送文件 + 控制注入 |
| 本地调试 | ADB input | 快速验证 |
| 压测并发 | MUA + SDK 混合 | MUA 跑业务,SDK 补充精确事件 |

## 六、双端协同等待机制

### 6.1 核心原则

**测试不影响正常业务**,因此:
- ❌ 不在 Device Platform 注册 webhook
- ❌ 不查询后端 API 验证状态
- ✅ 纯用户视角,通过 UI 截图轮询验证

### 6.2 轮询驱动实现

```python
def wait_for_pod_state(pod, expected_state, timeout_sec=30, interval_sec=2):
    """从 Pod UI 轮询状态,不依赖后端回调"""
    start = time.time()
    while time.time() - start < timeout_sec:
        screenshot = sdk.screenShot(pod)
        if mua_visual_check(screenshot, expected_state):
            return True
        time.sleep(interval_sec)
    return False
```

### 6.3 协同场景等待策略

| 协同场景 | 触发端 | 响应端验证(轮询 UI) | 超时 |
|---|---|---|---|
| 绑定 | Guardian 扫码 | K1 每 2 秒截图,检测"已绑定"提示 | 30 秒 |
| 内容下发 | Guardian 下发 | K1 每 2 秒截图,检测内容到达 | 30 秒 |
| 远程指令 | Guardian 下发 | K1 每 2 秒截图,检测"休息时间"提示 | 30 秒 |
| 拍照回传 | K1 拍照 | Guardian 每 2 秒截图,检测新照片出现 | 60 秒 |
| 报告回传 | K1 活动 | Guardian 每 2 秒截图,检测报告刷新 | 30 秒 |

### 6.4 轮询驱动的局限与补偿

**局限**:
- 2 秒间隔可能错过瞬时状态(如加载动画)
- 截图检测依赖 MUA 视觉理解,成功率 97.4%(非 100%)

**补偿措施**:
- 关键状态用 MUA + 视觉 diff 双重验证
- 超时后自动重试 1 次,仍失败才标记为 real failure
- 弱网场景单独测试,超时延长至 60 秒

## 八、云手机模拟 K1 的局限

### 8.1 无法模拟的维度

| 维度 | 影响 | 补偿方案 |
|---|---|---|
| 1.8GB RAM | OOM 风险不可见 | 真机 K1 补充性能测试 |

| 物理硬件按键触感 | 物理交互体验不可测 | 真机 K1 补充体验测试 |

### 8.2 测试覆盖策略

- **云手机负责 80%**:协同逻辑测试(UI、按键、音视频、网络协同)
- **真机 K1 负责 20%**:性能与兼容性测试(RAM、SoC、API 27、硬件体验)

## 九、关键风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| MUA 任务成功率 97.4%,非 100% | 偶发失败导致误报 | RetryLimit=3,失败用例自动重跑 2 次 |
| 单用户 QPS 限制 10/s | 压测并发上限 | 申请多个子账号,或采用阶梯加压 |
| 云手机无法模拟低端硬件 | 性能测试不可见 | 真机 K1 补充 |
| MUA 视觉理解依赖模型 | 复杂 UI 元素可能误判 | 关键断言双重验证(MUA + 视觉 diff) |
| TOS 截图链接有效期 24h | 长期证据留存 | 下载到本地 reports/<run-id>/ |
| 轮询驱动可能错过瞬时状态 | 状态检测不准 | 缩短轮询间隔至 1 秒,关键状态双重验证 |
| 双 APK 版本不匹配 | 协同测试失败 | 构建时强制版本匹配检查 |
